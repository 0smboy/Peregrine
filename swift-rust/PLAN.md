# Plan: Full Rewrite of OpenStack Swift in Rust

> Recovered from GitLab Duo session 5557568 and maintained in-repo from now on.
> Strategy: incremental "strangler" rewrite, wire- and disk-compatible, so Rust
> daemons can run inside a live Python Swift cluster and be validated
> component-by-component. Every serialized format is a compatibility contract,
> verified with golden fixtures generated by the real Python implementation.

## Verification strategy

- Golden-fixture round-trips for every serialized format (Python writes, Rust
  checks; then Rust writes, Python checks).
- Existing functional tests (`.functests`) run unmodified against Rust servers.
- Probe tests against mixed Python/Rust clusters for consistency daemons.
- Differential fuzzing of header/range parsing between swob and swift-http.
- Soak + fault injection before each component cutover.

## Working conventions (established Phase 0)

- One crate per contract, minimal dependencies, hand-rolled small error types.
- Every module header names the Python file it ports and lists deferrals.
- `tests/fixtures/generate.py` drives the *real* Python swift (python3.11 via
  mise, pbr+eventlet installed) to emit fixtures + `expectations.json`.
- Milestone = cargo test green + clippy clean + independent commit + ledger
  update here.

## Erasure coding (DONE on Linux, feature `ec`)

Built and verified on an AWS Rocky 9 box with liberasurecode compiled from
source (macOS has no liberasurecode, so this was the one environment-blocked
piece). All of it is behind a `ec` cargo feature — the default build and macOS
are untouched, and the whole thing links liberasurecode only when the feature is
on.
- **`swift-ec`** — liberasurecode FFI codec. `EcDriver::{encode,decode,
  reconstruct}` (single segment) and `{encode_object,decode_object,
  reconstruct_object}` (whole object → `k+m` fragment archives). Uses
  `liberasurecode_rs_vand` with `CHKSUM_NONE` (PyECLib's default), so the
  fragment bytes are **byte-identical to Python** (cross-checked 6/6). The fixed
  fragment header size is probed at driver creation so per-segment splitting is
  exact.
- **diskfile + object-server** — EC objects use `PolicyKind::Ec`; `put()` reads
  `X-Object-Sysmeta-Ec-Frag-Index` and `commit()` durablizes to
  `<ts>#<frag_index>#d.data`. `ObjectServerConfig.ec_policies` (built from
  swift.conf) selects the EC PolicyKind per policy index; the object auditor
  takes the PolicyKind so EC filenames parse.
- **proxy EC object controller** — `ec_put` encodes and fans a distinct fragment
  archive to each node (tagged with its index + the whole-object EC etag/length
  sysmeta), handoff fallback keeps a fragment's index, PUT quorum = `ndata +
  min_parity`. `ec_get`/HEAD gathers `ndata` fragments and decodes, surfacing the
  EC etag/content-length. e2e test (`tests/ec_integration.rs`): proxy + 6 object
  servers PUT a multi-segment object, all 6 durable fragments land, GET decodes
  from 4, and the object still reads after 2 fragments are destroyed on disk.
- **reconstructor daemon** (`swift-object-server::reconstructor`) — rebuilds a
  node's missing fragment: `discover_jobs` scans EC partitions and computes this
  node's fragment index from the ring; `rebuild_job` gathers `ndata` coherent
  peer archives, calls `reconstruct_object`, and persists the rebuilt fragment
  durably through the diskfile. Tested: the persisted fragment is byte-identical
  to the original PUT's.

EC follow-ups: ALL DONE — the multipart-MIME + multiphase-commit PUT
protocol, ranged EC GET, ssync fragment transfer (see the EC sections
below), and the three refinements (2026-07-23):

- **Rebuild-on-the-fly for ssync SYNC jobs** (`reconstruct_fa` /
  `sync_diskfile_builder` port): the sender's `SyncDiskfileBuilder` hook —
  `EcSyncRebuilder` gathers `ndata` coherent peer archives (required to
  match the offered fragment's timestamp), reconstructs the fragment at
  the RECEIVER's backend index, and sends the local datafile metadata
  with the frag index swapped and ETag removed so the receiver recomputes
  it (`RebuildingECDiskFileStream` parity). SYNC jobs now heal peers
  instead of only propagating tombstones/meta.
- **REPLICATE-scoped suffix comparison** (`_get_suffixes_to_sync` +
  `get_suffix_delta` port): SYNC jobs REPLICATE the partner, diff the
  per-frag-index suffix hash dicts, recalculate local hashes for the
  mismatches (invalidate + rehash), and ssync only the delta suffixes; a
  REPLICATE failure skips the partner (SuffixSyncError).
- **Partition lock**: `swift_core::lockutil::lock_path` — Python's
  `lock_path` with byte-identical `.lock`/`.lock-<name>` naming and flock
  semantics, so Rust and Python daemons on one node mutually exclude.
  Taken by the reconstructor's revert (name='replication', 0.2s — the
  Python `_revert` timeout), the replicator's handoff revert (15s), and
  the ssync RECEIVER for the whole exchange (15s, 503 on timeout —
  `Receiver.__call__` via `replication_lock`).

Remaining EC niceties (non-blocking, noted for completeness): the
device-level replication concurrency limiter
(`replication_concurrency_per_device`), handoffs_remaining /
max_objects_per_revert accounting in the reconstructor bin, and empty
partition-dir deletion after full reverts.

## Ranged EC GET + EC ssync fragment transfer (DONE 2026-07-23)

**Ranged EC GET**: client ranges fetch only the covered segment span —
source discovery keeps (frag index, node) pairs, the range maps to a
fragment-archive byte window, ranged fragment GETs feed the segment-wise
decoder, and a skip/limit trim yields the exact bytes. Single ranges
stream a plain 206; multi-range streams multipart/byteranges with each
part's fetch round opened lazily (framing byte-compatible with
swift_http::multipart_byteranges); 416 and the
X-Backend-Ignore-Range-If-Metadata-Present manifest rule preserved.

**EC ssync (the real, full-duplex protocol)**: swift-http gained
`Body::hijack` — the handler takes the raw connection write half while
the framed body reader stays live, enabling mid-request response
round-trips (the server then writes nothing and closes). On it:
- Receiver (`SsyncSession`): hijacked duplex exchange speaking Python's
  exact line protocol (missing-check wanted lines, updates apply,
  in-band `:ERROR:` lines with Python repr, failure thresholds);
  EC-aware per-frag-index missing-check porting `_check_local`'s durable
  fix-ups (a local non-durable fragment offered durably is committed in
  place; a non-durable local copy masks the offer), `X-Backend-No-Commit`
  PUTs store non-durable fragments, and the response advertises
  `X-Backend-Accept-No-Commit`.
- Sender (`ssync_sender.rs`): the Python Sender port over a pluggable
  `SsyncWire` (unit-testable), with the exact `encode_missing`
  hex-delta line format and chunked request framing.
- Reconstructor: `build_part_jobs` (`_get_part_jobs` port — one SYNC job
  for this node's frag index plus REVERT jobs per foreign index),
  `process_part_job` ssync-driven sync/revert with post-revert cleanup,
  and a new `swift-object-reconstructor` binary (per-EC-policy ring
  sweep, statsd/recon/SIGTERM like the replicator).

Verified: 779 local / 784 Linux workspace tests + 107 ec-featured, clippy
clean; 19 duplex/EC socket tests including rust↔rust sender/receiver

copy. **Wire-parity oracle on n2**: Python's own `ssync_sender.Sender`

## EC streaming + the real PUT protocol (DONE 2026-07-23): wire parity proven

The EC data plane now streams end-to-end AND speaks Python's actual backend
PUT protocol (multipart-MIME footers + two-phase commit), replacing the
plain-fragment contract:

- **swift-http**: `MimeDocs` (streaming multipart parser, document bodies
  never buffered) and `InterimResponder` (100 Continue with headers, sent
  repeatedly; each repeat send re-arms a finished chunked request body for a
  fresh chunked sequence — eventlet's `send_hundred_continue_response`
  semantics, verified on the wire). Connection teardown after an early
  response is FIN+drain so a mid-body 422/500 always reaches the client.
- **object server**: `X-Backend-Obj-*` headers switch PUT to MIME documents —
  object data streamed to the diskfile, a Content-MD5-guarded JSON footer
  (footer etag validates the streamed md5, footer sysmeta overrides headers,
  container-update overrides flow into updates and async_pendings), then for
  multiphase a second 100 Continue and a required commit confirmation before
  the fragment turns durable (`#d`). Policy-agnostic; tested over real
  connections including EC-kind durable/non-durable on-disk assertions.
- **proxy EC PUT** (obj.py `_transfer_data` port): MIME putters connect with
  Expect: 100-continue + capability checks, the client body is encoded one
  segment at a time and fragments teed per node (chunked framing; fragment
  archive size pre-declared when the client length is known), whole-object
  etag/length + container-update overrides travel as footers, quorum of
  phase-2 acks gates the commit. **EC GET** decodes segment-by-segment from
  `ndata` distinct streamed fragment sources — one segment of buffering.
- **Python parity fix**: zero-byte objects store zero-byte fragment archives
  (encode/decode/reconstruct all handle them; was header-only fragments that
  would OOB the reconstructor).
- **SWIFT_CONF fix**: all four server mains now default swift.conf to
  `$SWIFT_DIR/swift.conf` (was hardwired /etc/swift — a cluster rooted
  elsewhere silently read the wrong policies/hash keys).

## P1 streaming data path (DONE 2026-07-22): bounded-memory object I/O

The last production-readiness audit blocker. The entire data path was
store-and-forward `Vec<u8>` (5GB PUT ≈ 25GB proxy RSS; SLO GET concatenated
every segment; GET/HEAD read whole objects; no request deadline). Now the
object data plane streams end-to-end through 64KB buffers
(`rust/STREAMING_CONTRACT.md` is the API contract):

- **swift-http**: `Body` enum (Buffered|Streamed) on Request AND Response;
  the server hands request bodies to handlers as framed readers over the
  connection (Content-Length or chunked decode, `max_body_bytes` enforced
  during decode), answers `Expect: 100-continue` lazily on the first body
  read, streams response bodies (close-delimited when length unknown), drops
  HEAD bodies unread, reclaims connections for keep-alive (drain ≤64KB or
  close), and enforces a total request-head deadline (`head_deadline_secs`,
  the slowloris guard). Helpers: `materialize(cap)` (413 via
  `body_too_large`), `ChainReader`, `FnReader` (lazy pull chains).
- **object server**: PUT consumes the body as a streamed 64KB loop into
  `DiskFileWriter` (incremental md5, cumulative MAX_FILE_SIZE 413,
  short-body/client-disconnect 499 with nothing committed); GET streams via
  `DiskFileStreamReader` (quarantine-on-close preserved at stream EOF),
  single ranges via positional `DiskFileRangeReader` windows, multi-range
  206 via `ChainReader` byte-identical to the buffered oracle; HEAD never
  opens file contents.
- **proxy**: object GET hands the backend socket to the client as a
  CL-framed streaming body (decision logic — tombstone gating, handoff 404
  discard — reads headers only). Object PUT ports the obj.py protocol:
  connect all nodes with `Expect: 100-continue` (pre-body 412→412,
  409→202 Accepted, quorum of live putters or 503), then tee ONE 64KB read
  pass of the client stream to every live connection (chunked framing when
  the length is unknown; below-quorum mid-send→503, client disconnect→499),
  quorum the final responses. Control paths stay buffered.
- **middleware**: pipeline moved to `Arc`-based `NextFn` so SLO/DLO GET
  reassemble as lazy `FnReader` chains (each segment subrequest issued only
  when the client stream reaches it); copy/versioned_writes plumb the source
  GET reader straight into the destination PUT body.
- **P1-leftovers (still buffered, marked in code)**: ranged SLO/DLO GET and
  bulk delete lists. (EC PUT/GET streaming was completed 2026-07-23 — see
  the EC streaming section above.)

Verified: 757 workspace tests (mac, no EC) / 761 (Linux incl. EC feature +
EC e2e), clippy clean; live on the n2 probe cluster: probe replication set
19 passed / 0 failed (3 EC-only skips), functional 3-file regression
46 passed / 0 failed, and a NEW 1GB PUT/GET memory test — peak RSS delta
across all four servers: PUT +72 kB, GET +88 kB (was multi-GB), md5
integrity intact, PUT 13.5s / GET 3.1s.
